# Changelog

## Unreleased

### Fixed

- **`ocp update` told operators "THE PROXY IS DOWN … /health is not answering" about a proxy that had just answered (#372).** The forward path's DOWN cell keyed on `restartFailure && !postFlight.ok` — the `else`. `runPostFlightCheck` reports `ok: false` for seven distinct states and that sentence is true in two of them, so the cell fired on the **absence of a successful probe** rather than on evidence of non-reach. This is the fleet-rollout path, run unattended, and it is the same defect #352/#371 fixed on the rollback path a day earlier. Measured at v3.29.2, each with a restart command failing:
  - **answering with the wrong version** → "THE PROXY IS DOWN … not answering", inside the same thrown error whose own `post-flight` phase recorded `last saw version=3.10.0`. One error, two contradictory statements about one measurement — and the CLI's phase printer surfaces the hint, so the false half is the half the operator reads.
  - **answering with the RIGHT version but `status: "degraded"`** → the same sentence, about a proxy serving exactly the version that upgrade had just installed.
  - **answering with a non-JSON body** → the same sentence, while the phase message said "Something is answering on the port, but it is not this proxy."
  - `ocp`'s `cmd_restart`, which these cells cite as their authority, has never had this defect: its DOWN cell keys on the curl exit code (`probe_rc -ne 0`), not on a version predicate. So splitting the cell is the **faithful port** and `!postFlight.ok` was the embellishment. The forward path now carries the same five cells in the same order as the rollback path, with its own wording (its hints may end by pointing at `ocp update --rollback`, which the rollback path cannot say).

- **A kind name that made a claim the code could not back: `version-mismatch` covered three unrelated states (#372).** `runPostFlightCheck` stamped it on **every** post-body rejection, in one unconditional line — but the acceptance predicate `postFlightOk` rejects on `status` as well as version, and `/health`'s status domain is `{"ok","degraded"}`, always over HTTP 200. A right-version/degraded proxy, a wrong-version proxy and a JSON body carrying no `version` field all arrived under one name. #371 reconstructed the missing distinctions inside `runRollback`'s own cells; that left the misnomer in place for `runFullUpgrade` and for `postFlightFailureSuffix` — **the renderer bash's `ocp update` delegates its final verdict to** (`_cmd_update_light` / `_cmd_update_restart` both report whatever `--post-flight-only` says). Split into `version-mismatch`, `not-ok-status` and `body-not-ocp`, so a cell can key on a kind and get what the kind says. A status-only rejection now claims nothing about versions on either path.

- **A predicate satisfied by a missing operand: `SERVING THE WRONG VERSION (3.10.0, expected )` (#372).** `servedWrongVersion` was `lastSeen !== postFlight.target`, and `readSnapshot` returns `null` for `fromVersion` when `from-version.txt` is unreadable (`scripts/lib/snapshot.mjs`'s `catch { return null; }`), so `target` is `""` and the `!==` is true for any version at all. Fixed **in the classifier rather than in each cell**: `version-mismatch` is now only stamped when two present versions were compared and differed, so every caller inherits the property instead of having to re-establish it. Worth stating because it is the counter-example to the obvious structural fix — splitting the classifier by *kind* would not have caught this, since the defect was in the other operand.

- **A valid JSON `null` body was reported as the proxy being DOWN, with a JS `TypeError` as the operator-facing detail (#372).** `lastSeen = body.version` had no optional chaining, so `null` threw; the throw was caught by `classifyPostFlightProbeFailure` two lines down, fell to its default arm, and produced `{kind: "unreachable", detail: "Cannot read properties of null (reading 'version')"}` — DOWN, for something that answered. (Same JSON-scalar shape as #360, on a different surface.)

- **`postFlightFailureSuffix` narrated answers as `unreachable`, on the lane bash reports verbatim (#372).** Its `if (result?.lastSeen)` ran ahead of the switch — the same negation shape one layer out, firing on the presence of a value `runPostFlightCheck` never resets — and its `default:` arm caught everything else. A body with no `version` field rendered `" (unreachable — serving unknown)"`. It is now keyed on the classification; the `version-mismatch` text is preserved **byte-for-byte** (it was already correct, and a test pins it), as are the no-classification fallbacks.

- **Two hints named a `--post-flight-only` invocation that cannot check anything (#372).** With an absent target they rendered `--post-flight-only null` and `--post-flight-only v`, and nothing downstream catches either: the CLI's guard fails closed only on a *missing* or `--`-prefixed value, while `"null"` can never match a real version and `"v"` v-strips to `""`, which `postFlightOk` deliberately degrades to the serving check alone — so the advice given at the operator's least-informed moment would report success against **any** version. The clause is now omitted when there is no version to name. Reachable in production on the rollback path (unreadable `from-version.txt`); on the forward path reachable through `mockDoctor` but **not** demonstrated reachable in production, and the code says which is which.

- **`nothing will start it on its own` was still asserted for both service shapes on the forward path (#372).** #352's LOW-1 fixed this on the rollback path only. `scripts/lib/install-autostart.mjs` writes `Restart=always`/`RestartSec=5`, and `recoveryPlanCommands`' own start-limit arithmetic *depends* on systemd restarting the unit by itself — so the claim contradicted a premise this file already relies on. Stated per shape: true on launchd, where a succeeded `bootout` unloads the job.

- **`unreachable` was the probe classifier's DEFAULT arm, so `THE PROXY IS DOWN` still fired on an `else` (#372, found by #381's independent review).** The DOWN cell was re-keyed onto the kind — and the kind itself was a claim nothing established: `classifyPostFlightProbeFailure` returned `unreachable` for curl exit 7 **and for everything it did not recognise**. Measured: a spawn `EAGAIN` or `ENOMEM` (the probe process could not be started at all — a purely local fault, and the fleet includes Pis), curl 52 (empty reply) and curl 56 (connection reset) — the last two meaning the peer *accepted* the connection — all reported the proxy as down. `unreachable` now means only "curl said it could not connect"; spawn failures are recognised as local by the absence of an exit status plus an errno; everything else gets `probe-failed-unclassified`, which no cell routes to DOWN. This is the same defect the same PR fixed for `version-mismatch`, one branch over in the same function — the rule was applied to the kind being looked at and not to the one beside it.

- **A degraded proxy already serving the new version was told to roll back (#372/#381).** With no cell of its own, `not-ok-status` fell to the forward path's neutral arm, whose hint is *"Run `ocp update --rollback`"*. The upgrade's code **is** what is running, and a rollback cannot clear a degraded status — that comes from the `claude` binary being unusable or from repeated auth rejections, neither of which the tree version decides. The state now has its own cell naming what is serving and pointing at `ocp doctor`. (The rollback path needed no equivalent: its neutral verdict already says `ocp doctor`.)

- **Non-string `version` values were coerced into the version comparison (#372/#381).** `postFlightOk` compares `body?.version === want`; the classifier compared `String(body.version) !== want`. Measured against target 3.29.2: `version: ["3.29.2"]` coerced *equal* and fell through to a status rejection rendering *"reported status=ok, not status=ok"*; `version: []` produced `SERVING THE WRONG VERSION (, expected 3.29.2)` — the same empty-operand rendering this issue was filed to fix, on the other operand; `version: {}` produced `[object Object]`. `/health` answers with a version **string**, so anything else is now `body-not-ocp`.

- **The "will anything start it on its own?" note was a two-way answer over a three-way domain (#372/#381).** `planRestart` returns `launchd`, `user-unit` or `system-unit`, and the non-launchd branch asserted `Restart=always` for both. OCP installs only the **user** unit; a `system-unit` is whatever `resolveOwningUnit` found holding the port, and OCP never reads its `Restart=` directive — so on a host with a hand-written unit carrying `Restart=on-failure` the hint claimed systemd might recover it. Now answered per shape from one shared helper, with the discovered-unit case stated as unknown and the launchd case hedged, because the resolved `bootout`'s exit status is discarded (`|| true`) and this note only renders when a restart command has already failed.

- **`ocp update`'s `--post-flight-only v` reported success against any version (#372/#381).** The CLI's fail-closed guard rejected a missing or `--`-prefixed target, but `"v"` is neither; it v-strips to `""`, which `postFlightOk` degrades to the serving check alone. Measured against a live proxy: `✓ service now serving v`. The guard now also rejects a target that v-strips to nothing.

- **Not endpoint-touching.** `scripts/upgrade.mjs` is the `ocp update` CLI dispatcher; `server.mjs` is untouched by this change. No `ALIGNMENT.md` rule is invoked and no ADR is cited, because none governs this surface.

## v3.29.2 — 2026-08-10

### Fixed

- **The COMPLETION text was silently corrupted whenever a character straddled a chunk boundary on the child's pipe (#365, the other half of #359).** `lineBuffer += d.toString()` and `stderr += d` in `callClaude` and `callClaudeStreaming` decoded each `Buffer` from the spawned `claude` **independently**, so a multi-byte character whose bytes arrive in two `'data'` events became replacement characters before the pieces were joined — and joining cannot repair it. #359 fixed the request side, which corrupts the prompt; this is the answer side, which corrupts what the model said on its way to the client. Just as silent: the NDJSON line stays syntactically valid, nothing throws, nothing logs.
  - **Two lines at the shared spawn boundary, not four at the readers.** `spawnClaudeProcess` is the sole spawn site for the `-p`/stream-json path and `callClaude` + `callClaudeStreaming` are its only two callers, so `proc.stdout.setEncoding("utf8")` + `proc.stderr.setEncoding("utf8")` there cover all four accumulators. `setEncoding` installs a `StringDecoder`, which holds an incomplete trailing sequence until the next chunk completes it.
  - **This is not "no consumer-visible change".** A `stream-json` line long enough to be split mid-character used to deliver altered text to the client — a wrong `choices[0].message.content`, or a wrong SSE `delta.content`. It now delivers what the child wrote. The *contract* is unchanged: no field added, removed, renamed, retyped, or re-ruled, and no field's documented meaning moves.
  - **What each of the four accumulators feeds was checked before changing it, because `stderr`'s type is load-bearing in ways `body`'s was not.** The two `lineBuffer`s feed `parseStreamJsonLines` → the completion text and the SSE deltas. The two `stderr`s are string-sliced at 300, logged via `logEvent`, passed to `trackError` (which re-slices at 200 into `/status`'s and `/health`'s `recentErrors[].message`), run through `sanitizeError`, and turned into an `Error` message that becomes a 500 body or an SSE error frame. None of it constrained the fix: `stderr` starts as `""`, so `+= Buffer` **already** coerced with `toString("utf8")` — it was always a string, and it still is. Only the bytes are now decoded across chunk boundaries instead of per chunk. Every one of those consumers is pinned by a new test.
  - **End-of-stream is a decision, and it is not #359's.** Node flushes a still-incomplete sequence at EOF (`onEofChunk` calls `decoder.end()`) rather than dropping it, and keeping the flush is right on both streams for different reasons. On **stdout** it is inert: a truncated final line has no terminating newline, so `parseStreamJsonLines` already leaves it in `remainder`, which is discarded — a child that died mid-write therefore still surfaces as its real cause (non-zero exit / no `result` event) and never as a spurious NDJSON parse error. #359 rejected a truncated request body precisely because a drop would let a truncated body pass as complete; here the truncated line is *already* discarded, so there is nothing to mistake for complete and nothing to gain from failing the request. On **stderr** the flush is observable, and dropping would silently shorten a diagnostic, so the flushed substitution character is kept — which also leaves the message byte-identical to today's whole-buffer decode.
  - **Tests control the child's chunk boundaries.** A fake `claude` writes its stdout/stderr from files in two `cat`s separated by a real gap, so the test picks the byte offset at which the pipe is cut, and the files are re-staged per case while the server stays booted. Both the buffered and the streaming path are swept, over a payload carrying a 2-byte, 3-byte and 4-byte character; the stderr path additionally asserts the exact `sanitizeError(stderr.slice(0,300))` output, the SSE error frame, and `/health`'s `recentErrors[].message`. A control child reproduces the pre-fix accumulation verbatim and must corrupt at exactly the offsets the two-chunk join predicts, and must report >= 2 `'data'` events — so a coalesced write or an immune payload fails loudly instead of passing vacuously.
  - **The sweep is provably sufficient rather than exhaustive, and that was a measurement, not a preference.** Each offset costs a real child spawn per path, so cutting at literally every byte offset is ~300 spawns; with that in place, 2 of 6 full runs on a host at load average ~11 produced *unrelated* failures of a class this suite already documents (`_runStartShScenario` polls for a backgrounded `node` to be scheduled, and its own comment records that poll flaking on a loaded host), while the unmodified base tree produced none in 2 runs under the same conditions. The sweep now cuts at every continuation-byte offset — the only offsets at which this defect can corrupt anything — plus the offset either side of each character and a stride sample of the remainder: 24 offsets instead of 101, and 72 child spawns instead of 303. Sufficiency is asserted rather than argued: the set of offsets the pre-fix join corrupts is computed over *all* offsets in-process and every one of them must be in the swept set, so narrowing it again cannot silently drop coverage.
  - **Class B, both sub-buckets, route (a).** The completion body is B.1 — `POST /v1/chat/completions`, OpenAI's spec + ADR 0006. Five grandfathered B.2 responses carry corrected values downstream, none of them edited by this change: `recentErrors[].message` on `/health` and `/status`, the `stderr` field of the `claude_exit` log entry on `/logs`, and the character totals behind `/api/usage` and `/cache/stats`. Every one of those rules ("the error message, truncated"; "characters in the response") is untouched while its value stops being corrupted: ADR 0006 (grandfathered as of v3.16.4), **route (a)**, the same shape as the `stats.activeRequests` worked example in `CLAUDE.md`. No field is added, so ADR 0012 is not engaged.
  - **Found by this PR's own independent review, and fixed in it:** the streaming sweep asserted neither of the two non-vacuity premises the other three tests assert, so mutation M4 — which disables the harness's split entirely — left it printing a green tick while testing nothing. The evidence was already in the mutation table (M4 reddened three tests, not four) and the conclusion had not been drawn from it. It now measures both premises per offset like its sibling. The review also corrected a comment claiming the retained `d.toString()` protects a future caller that forgets `setEncoding`; it does not — with a `Buffer` that expression *is* the defect — and the guarantee lives only at the spawn boundary.

- **The same one-shot restart loop was still in `ocp update --rollback` — the *recovery* path (#352).** #347 fixed `runFullUpgrade`. `runRollback`, in the same file, kept `for (const c of restartPlan.plan.cmds) exec(c.cmd, c.label)` byte for byte, with an `exec` that throws. That is the path `ocp update`'s own failure hint tells the operator to run: it is invoked *because* the forward path already failed, by someone who has just been told the proxy is not running. A one-shot restart there turns a recoverable outage into a longer one, and its failure message — `rollback phase restart failed` — is a statement about a command, not about the service.
  - **The throw also made #274's post-flight unreachable.** `runRollback` has had its own `runPostFlightCheck` call since #274, added precisely so a rollback could not report success without confirming what is serving. On a restart-command failure the throw jumped past it, so in the one case that measurement existed for, nothing measured. It is now reached whether or not a restart command failed (its `mockExec` gate is unchanged).
  - **Retry, restoration and the outcome cells, ported from #347** — `execRestartRetry` with `RESTART_ATTEMPTS` and rising backoff, a bounded `restart-restore` pass after a settle delay, and a verdict that comes from the probe rather than from a subcommand's exit status: probe could not **run** → **UNKNOWN**, never DOWN, checked first so a host with a broken `curl` is never told its proxy is dead; something answering with the wrong version → **UP BUT SERVING THE WRONG VERSION**; nothing answering → **THE PROXY IS DOWN**; answering correctly → warned success, not a silent `✓`. `git checkout`, `npm install` and the MED-E `daemon-reload` are deliberately untouched and still fail fast.
  - **Every verdict is keyed on the #291 classification of the last probe attempt, so no sentence asserts more than was measured.** `postFlight.ok === false` covers five states and the DOWN wording ("/health is not answering") is true in only two, so a five-cell ladder replaced the single `!ok` test: `probe-could-not-run` → UNKNOWN (checked first, so a host with a broken `curl` is never told its proxy is dead); a body rejected for its **version** → UP BUT SERVING THE WRONG VERSION; a non-JSON body, a non-2xx, or JSON with no `version` field → **SOMETHING ELSE IS ANSWERING**, whose remedy is `ocp doctor` and finding the port's owner rather than another restart, because recovery commands cannot bind a port someone else holds; `unreachable`/`timeout` → THE PROXY IS DOWN. DOWN requires positive evidence of non-reach rather than being the `else`.
  - **Two of those cells exist because the first two attempts at this were wrong, and both were caught by review rather than by test.** The DOWN cell first fired for a non-JSON body — an error whose phase message said "something is answering … but it is not this proxy" while its hint said "/health is not answering", with the CLI printing only the hint. It also broke the authority being cited: `ocp`'s `_curl_probe` returns 0 whenever `curl` exits 0, and `curl -sf` exits 0 on a 200 with a non-JSON body, so bash reaches warned-success and *cannot* reach its DOWN cell. Then the wrong-version cell fired for a correctly rolled-back but **degraded** proxy, printing "SERVING THE WRONG VERSION (3.10.0, expected 3.10.0)" — because `runPostFlightCheck` labels every post-body rejection `version-mismatch` while `postFlightOk` also fails on **status**, and `/health` reports `degraded` over HTTP 200. The shared classifier's conflation of the two is recorded on the follow-up issue rather than fixed here, since it is reached by `runFullUpgrade` too.
  - **The hints are not copied, because the forward path's hints end in advice this path cannot give.** `runFullUpgrade` closes by pointing at `ocp update --rollback`; here that is the command already running, and repeating it sends the operator round the same loop. The DOWN hint says instead that the working tree is **already** rolled back to the snapshot's version and the only thing outstanding is a running service. The probe-could-not-run cell says `THE ROLLBACK MAY HAVE SUCCEEDED — do NOT re-run it on this evidence` rather than the pre-#352 message, which asserted the restored tree might not be what is running — a claim about the tree, emitted for a fault in the local `curl`. The DOWN hint also no longer claims "nothing will start it on its own" on the systemd shape, where `install-autostart.mjs` writes `Restart=always`.
  - **A failed rollback DOES auto-restore, argued rather than inherited.** It is the last automated step there is — declining to attempt the repair hands the operator a hint they have already followed once — and the commands bring up the **old** tree, already checked out and installed, so there is no "wrong version came back up" hazard for it to weigh, which the forward path does have. It is bounded exactly as #347's is. (A first draft also argued that `allowNotListeningFallback: isRollback` proved the service must already be down here; it does not — that flag *permits* the not-listening case without establishing it, and the ordinary rollback reverts a service that is very much listening. Corrected before merge; the two reasons above carry the decision on their own.)
  - **On a user unit the executed restoration pass clears the start limit first, which #347's forward path does not do.** Deliberate divergence, forced by the arithmetic in this feature's own design note: the retries plus the restoration pass plus systemd's `Restart=always` restarts land inside one 10 s window, and once the limit trips a plain `systemctl restart` keeps failing — so a restoration pass that is the fourth such invocation is expected to be a no-op, leaving the repair only in the printed text. Running `recoveryPlanCommands`' list makes the attempted repair and the printed one the same commands. Scoped to `user-unit` and **not** `system-unit`, because there the list would emit `sudo systemctl reset-failed`, a different `sudo` command from the `sudo systemctl restart` that `planRestart` verified with `sudo -n -l` — a password prompt, i.e. a hang, in a recovery path. What actually keeps `sudo` out of this function is narrower than the first draft claimed, and an independent review measured the overstatement: the retry loop and the restore's `else` branch execute the plan's commands verbatim, and a `system-unit` plan carries `sudo`. The property rests on `resolveRestartPlan` refusing `isRollback && owner.kind === "system-unit"` before any command runs — so that refusal is what now carries a test with teeth (it must fire with **zero** commands executed). The first clause holds; the second assumes every boot is separated from every other boot by a drain, and **five sites boot a second child inside a single test body**, where the between-test barrier never runs. All five were `ltWait(() => buf.closed, 5000)` with the boolean discarded — the same defect one scope down — and a comment already in the file documented the counterexample verbatim. ## v3.29.1 — 2026-08-06

### Fixed

- **UTF-8 was silently corrupted whenever a character straddled a chunk boundary (#359, P0).** All four request-body readers accumulated with `body += chunk`, which coerces each `Buffer` to a string **independently**. A multi-byte character whose bytes arrive in two chunks is decoded as replacement characters *before* the pieces are joined, so the join can never repair it: `你好世界` became `\uFFFD\uFFFD\uFFFD好世界`. Each of the four readers now calls `req.setEncoding("utf8")`, which installs a `StringDecoder` on the stream so an incomplete trailing sequence is held until the next chunk completes it. Sites: `PATCH /settings`, `POST /v1/chat/completions`, `POST /api/keys`, `PATCH /api/keys/:id/quota`.
  - **This is not "no consumer-visible change".** A body split mid-character used to corrupt, and depending on where the split landed either altered the prompt handed to the CLI or failed `JSON.parse` with a 400; it now parses. The *contract* is unchanged — no field added, removed, renamed, retyped, or re-ruled — but the values stop being wrong, which is observable.
  - **The caps deliberately still count characters.** All four compare `body.length` — UTF-16 code units, not bytes — and #310 exists because mislabelling that quantity cost two review rounds. Accumulating `Buffer`s and calling `Buffer.concat` at the end would have changed the unit (a ~3x tightening for CJK) **and** deferred the limit check past end-of-stream, removing the early abort. `setEncoding` delivers already-decoded strings instead, so `body += chunk` and `body.length` keep their exact previous meaning. Regression-tested on all four routes: exactly-cap multi-byte bodies stay accepted, cap+1 stays rejected.
  - **No body accepted today can newly receive a 413.** Verified over 200,028 split points (all offsets of fixed payloads plus 200,000 random byte strings): the pre-fix accumulation never produced *fewer* characters than a correct decode, only more. The change can therefore only admit bodies that were previously rejected in error.
  - **Decided behaviour for malformed and truncated input, because neither is obvious.** Bytes that are not valid UTF-8 decode to U+FFFD exactly as a whole-buffer decode already did, and the result is now identical no matter where the stream was cut. A body that *ends* mid-character is **rejected**, not silently accepted: Node flushes the buffered partial sequence at end-of-stream (`readable.js` `onEofChunk` calls `decoder.end()`), the substitution character breaks `JSON.parse`, and the request gets a 400 — a truncated body must not be mistaken for a complete one.
  - **The child `stdout`/`stderr` accumulators have the same defect and are deliberately not touched here** — the `proc.stdout.on("data", …)` and `proc.stderr.on("data", …)` handlers inside `callClaude` and `callClaudeStreaming` in `server.mjs`. Cited by function rather than by line on purpose: `ALIGNMENT.md`'s note on line-number rot applies with force to a CHANGELOG, which outlives every line number in it, and #359's own line references (`:1761`, `:1787`, `:2234`, `:2303`) were already 16 lines stale against this PR's base. Setting the child streams' encoding once at the shared spawn boundary is a separate, smaller change, and both `stderr` accumulators are string-sliced and turned into `Error` messages, so their type is load-bearing in ways the body readers' is not. #359 stays open to cover them.
  - **Tests control the chunk boundaries, because the pre-existing CJK coverage structurally cannot.** It sends whole bodies through `fetch()`, and a body that arrives whole cannot exhibit the defect. The new tests drive a raw socket, split at **every internal byte offset** of 2-byte, 3-byte and 4-byte characters plus invalid and truncated byte sequences, and assert against a control server in the test process that reproduces `body += chunk` verbatim — the control must corrupt at exactly the offsets the pre-fix operation corrupts, and must report >= 2 `data` events, so a coalesced write or an immune payload fails loudly instead of passing vacuously.
  - **Class B, both sub-buckets.** `/v1/chat/completions` is B.1 (OpenAI spec + ADR 0006); `/settings`, `POST /api/keys` and `PATCH /api/keys/:id/quota` are B.2, authorized by ADR 0006 (grandfathered as of v3.16.4), **route (a)** — behaviour-preserving in the contract sense, the same shape as the `stats.activeRequests` worked example in `CLAUDE.md`. ### Added

- **A non-primary OCP instance can declare itself (#327).** New env var `OCP_INSTANCE_NAME`, reported on `/health` as **`instanceName`** — **additive under ADR 0012** (additive only, read-only, no new endpoint or method, reports on what `/health` already reports on: `version`, `architecture`, `authMode`, `claudeBinary` are all instance-scalar facts, B.2 only).
  - **The issue said this needed its own ADR. Overriding that was right; the reason first given for it was false.** The PR originally dismissed the issue's reservation as "written before ADR 0012 was signed off". Measured: ADR 0012 landed on main at 09:48Z and issue #327 was opened at 10:35Z — **47 minutes later**, never edited, and its text **cites ADR 0012 by name** while carving out "a new *env-driven* field with new semantics deserves the check". It was a considered reservation made with 0012 in hand, not a stale opinion. Engaged on its merits instead: ADR 0012's conditions recognise no "env-driven" carve-out, and condition 4's "new subject in an additive costume" targets surfacing a **new subsystem** — while `/health` already reports `authMode`, `claudeBinary` and `config.*`, all operator-configured env-derived instance-scalar facts. `instanceName` is the same species: a static reflection of unit configuration with nothing behind it and nothing branching on it. The future `doctor`/sweep consumers are separate changes needing their own authorization when they arrive.
  - **The reason a second instance exists is Unix identity, not load.** OCP spawns a `claude` child per request and that child inherits the *service's* identity, so an agent answering untrusted users needs its own instance under its own user. That cannot be solved inside one process — the spawn identity comes from the unit's `User=`, one identity per unit.
  - **Two things this fixes, both of which happened.** A version sweep probing only `:3456` reported the fleet clean while a second instance sat a full release behind. And `ocp doctor`'s multi-unit check has no vocabulary for "two instances, both intended", so it warns on a correct configuration every run — and a warning that always fires is one people learn to skip, which is how the *genuine* leftover duplicate on that same host stayed hidden.
  - **Empty rather than omitted** when unset, so a consumer can distinguish "this is the primary" from "this build predates the field" — the same distinction #324's backward-compatibility test turns on. A mutation to the tempting `...(x ? {x} : {})` shape turns a test red.
  - **Scope, stated:** this makes an instance *discoverable*. Teaching `doctor` to tell declared multiplicity from a leftover duplicate needs a unit→instance mapping it does not have, and is deliberately left as follow-up on #327 rather than half-built here.
  - README gains a "Running more than one instance on a host" section documenting the `DEFAULT_PORT + n` convention, why the identity boundary is the reason, and both failure modes above.


### Fixed

- **The `auth` state table was keyed on the wrong field, and promised a value the server can never emit (#342).** `README.md`'s § "What `auth.ok` means" was keyed on `lastOutcome`, but the field the verdict's meaning turns on is `okSource`. Two rows were wrong as a result, not one.
  - **`lastOutcome: "verified-by-request"` does not exist.** `grep -c` in `server.mjs`: **0**. It was promised by the README table, by ADR 0014 § C bullet 1, by this CHANGELOG's own #308 entry, and by a comment in `lib/spawn-auth.mjs` — which sat **three lines above** another comment saying not to key on `lastOutcome`. The implementation is the correct one here: `noteAuthVerifiedByRequest` leaves `lastOutcome` to the probe, because overwriting it would make `/health` claim a probe ran when none did. Writing the value in code would have reintroduced exactly the lie #308 was about.
  - **The table had no row for the state most instances are actually in.** Once a completed request raises the verdict on a host that supplies the token through the environment, the real state is `ok: true` + `okSource: "request"` + `lastOutcome: "token-present"` — a pairing the old table's `token-present` row explicitly contradicted by asserting `ok` is `null`. Three of the four instances in the reference fleet spend most of their time there. A monitor written from that table could not match reality, and the state it would see most often was the one missing.
  - Re-keyed on `okSource` with all six reachable states enumerated, `lastOutcome` demoted to a secondary column, and inconclusive probes explained as changing only that column rather than being a row. ADR 0014, the CHANGELOG entry, the `spawn-auth.mjs` comment and three test fixtures carrying the phantom name are corrected in the same PR. No behaviour changes — `applyRequestVerdictTtl` already keyed on `okSource`; suite green before and after at 1041.

- **The ADR 0012 additive-field sweep had two defects, found on its first real run, pushing the count in opposite directions (#338).** The sweep was introduced last release to make B.2 surface growth visible, and its first use miscounted.
  - **Case-sensitive grep ⇒ under-count.** The prescribed literal missed `**Additive under ADR 0012.**` — capital `A`, because the marker opened a sentence. A real shipped field (`auth.consecutiveInconclusive`, #324) vanished from the audit. This is the dangerous one, and it fires on the **compliant** path: the author wrote the marker exactly as ADR 0012 condition 5 requires. It was caught only because a reviewer re-ran the grep with different flags — which is not a control.
  - **Counting its own prose ⇒ over-count.** A CHANGELOG entry describing the sweep necessarily quotes the marker it greps for, which would have put a permanent +1 into the cumulative total.
  - Both corrupt the one number ADR 0012 names as load-bearing: *"a monotonically rising integer is what makes the accumulation visible at all."* The `how:` clause now specifies case-insensitive matching, counting **entries** rather than occurrences, reading every hit rather than reporting the raw number, and stating the raw-vs-reported difference when they diverge. **A known-good baseline is anchored in the clause** — 2 as of v3.29.0, `instanceName` and `auth.consecutiveInconclusive` — so future releasers increment a fixed number instead of recomputing it with whichever flags they happen to use, since that recomputation is what produced both defects.

- **A duplicate `auth:` key in `/health` had silently disconnected the fix immediately below it (#339).** Caught by adversarial review of this batch **before the tag was pushed**, and confirmed by mutation on the live wire rather than by reading the diff: with `effectiveAuthStatus()` stubbed to return a marker, the marker did not appear in the response — the raw `authStatus` latch was being served instead. JS object literals keep the **last** duplicate key, with no error and no warning, so `auth: effectiveAuthStatus()` was computed and thrown away.
  - **Provenance:** #334 changed `auth: authStatus` → `auth: effectiveAuthStatus()`. #336 was written against pre-#334 code and its hunk re-added the old line alongside `instanceName` — a rebase-conflict artifact in a hand-resolved merge.
  - **Consequence had it shipped:** `/health`'s auth verdict would never expire. ADR 0014 § "Why the raise must expire" exists for exactly the state #324 observed on a real host for hours — a request-verified `ok: true`, then an expired token, then *inconclusive* probes that preserve `ok` indefinitely. The read-time TTL was the **only** guard for that shape. `/health` would report `auth.ok: true` while nothing could be served, and `ocp doctor` would read that body and report `PASS`. Byte-for-byte the #308 symptom, re-opened by #308's own release batch.
  - **Why 1040 green tests missed it:** `applyRequestVerdictTtl` is unit-tested and correct. Nothing asserted that `/health` *calls* it. The TTL-applied and raw values are identical in every state a live test can reach inside test time, so no live assertion could tell them apart.
  - **The wiring is now pinned behaviourally** (#340). The test posts a request to raise the verdict, steps the child's clock past the freshness window, and asserts `/health` reports `okSource: "expired"` / `ok: null`. It fails against both shapes of the defect — the original `auth: authStatus` and the quoted `"auth": authStatus` — and takes about six seconds.
  - **The first attempt at this shipped a source-grep guard instead, on a justification that was reasoned rather than executed.** It claimed no state was reachable in test time where the TTL-applied and raw values differ. Independent review executed the claim and it was false: `ltBoot`'s third argument lands before the script, so `--import` can step the child's clock with no production change, no env knob and no new ADR. The guard is deleted; it also had a proven bypass — `"auth": authStatus` counts as one key and still serves the latch — which is exactly what a source-text check cannot see and a behavioural one cannot miss. Recorded because the failure mode being fixed here and the failure mode of the first fix are the same one: **a thing that looks verified because something adjacent to it was verified.** #343 sweeps for other helpers that are correct, tested, and unpinned at their call site.

- **`/health` reported `auth.ok: true` on hosts where no request could be served (#308, ADR 0014).** Root cause, measured rather than reasoned about: **`claude auth status` reports whether a token is PRESENT, not whether it is VALID.** In an isolated empty `HOME`, with no token it exits 1 (`loggedIn: false`); with a **fabricated** token — a string that never existed — it exits **0** and reports `loggedIn: true, authMethod: "oauth_token"`.
  - Everything in the report follows. The service carries `CLAUDE_CODE_OAUTH_TOKEN` in its `EnvironmentFile`, the probe inherits it, the child sees a token and exits 0. The same binary run by hand in an interactive shell has no such variable, falls back to an empty `~/.claude/.credentials.json`, and exits 1. The token was **present and expired** — presence is what the probe measured, validity is what the request needed.
  - **Not one host: all three Linux hosts in the fleet use that mechanism.** On any of them `auth.ok: true` meant "a token is set", and would have kept saying so indefinitely after expiry.
  - **The probe now reports what it measured.** When the child's credential came from the environment, exit 0 yields `auth.ok: null` / `lastOutcome: "token-present"` instead of `authenticated`. `null` is not a new state — ADR 0010 already defines it as "no conclusive verdict" and `ocp doctor` already treats it as WARN, not FAIL, so it does not block `ocp update`.
  - **A completed request is now conclusive evidence**, and free: it was happening anyway. A successful completion sets `auth.ok: true` / `okSource: "request"`, and deliberately leaves `lastOutcome` as the probe set it — overwriting it would make `/health` claim a probe ran when none did. So on an env-token host the steady state is `okSource: "request"` + `lastOutcome: "token-present"`, and that pairing is normal.
  - **The guard that was supposed to make provenance un-droppable could not see the hardest branch.** Its pattern matched `authStatus = {…};` and so structurally could not match the token-present write, which is a *ternary* — 4 of 5 assignments matched, and a `>= 4` floor let the most complex branch pass invisibly. Now an exact count of 5 over `authStatus = …;`, plus a behavioural assertion on that branch's own fields, so the contract does not rest on a source pattern at all. A mutation dropping the fields from exactly that branch now turns the money test red.
  - **The verdict's provenance is a separate pair of fields from the probe's outcome** — `auth.okSource` (`none`/`probe`/`request`/`expired`) and `auth.okAt`, alongside the existing `lastOutcome`/`lastCheck`. This is not tidiness: keying the freshness window on `lastOutcome` made it a fiction in two ways, both caught by independent review and both proven by execution. **(a)** Every probe completion rewrites `lastOutcome`, and a probe always completes within ~610s by default — shorter than the window — so the decay branch was **unreachable**, and the docs described a semantic the system did not have. **(b)** Worse, a single inconclusive probe disarmed it *permanently*: the inconclusive branches preserve `ok` (correctly) while rewriting `lastOutcome`, so a request-established verdict stopped matching and stayed `true` forever — replayed, `T+100h` still read `auth.ok: true`. That is the unbounded false `true` this whole design exists to prevent, reintroduced by its own guard. Keyed on `okSource`/`okAt`, the same replay now expires at `T+16min`.
  - **An exit-0 probe resets the rejection tally on both branches.** The first implementation preserved it on the token-present branch, silently removing ADR 0010's self-healing on exactly the hosts that use the env-token mechanism — once the tally reached the degrade threshold nothing could lower it, because a successful probe was the only thing that did. A successful request clears it too.
  - **A probe never overwrites a fresher request verdict.** The token-present branch measured less than a recent completed request; letting it clobber that would contradict this change's own evidence hierarchy.
  - **That verdict expires after 15 minutes, and the expiry is the load-bearing part.** Without it the design creates a latch strictly worse than the bug it fixes: a proxy serves, the verdict is raised, the token later expires, requests start failing — and *nothing can lower it*, because the probe still sees a token present and cannot contradict a stale `true`. That state is byte-identical to what #308 reported, reached by a different path. This is #324's shape in the opposite direction, and its criterion applies: do not ask what the clearing condition is, ask whether it is **reachable**.
  - The expiry is a **pure injectable function**, not an env var. The window has to be testable at arbitrary values without becoming an operator knob — a knob on a safety decision is a knob for turning the safety off, the same argument ADR 0010 makes for `AUTH_DEGRADE_AFTER`.
  - **`/health`'s `status` cannot be moved by any of this.** `proxyHealthStatus` reads `consecutiveFailures` and never `ok`, so no verdict change here can flip a host to `degraded`. It does **not** follow that the tally is untouched — an exit-0 probe resets it on both branches and a successful request clears it, which is a deliberate restoration of ADR 0010's self-heal. An earlier revision of this line said "nothing here writes that tally"; that was false, and it survived one round after the commit message that introduced the fix had already named it as concealment.
  - Request *failures* deliberately do **not** lower the verdict. `server.mjs` does not classify a child's failure — it rejects with raw `stderr` — so doing that would mean matching text in another program's error output, and two reproduction attempts (fabricated token, no credentials) both **hung** rather than failing in any classifiable way. The asymmetry is safe in the right direction: the change can only raise confidence on conclusive evidence, never lower it on evidence nobody understands. ADR 0014 records this as an open question rather than guessing.


- **`ocp restart` no longer leaves the service DOWN when the start half fails (#325).** A restart is stop+start; when the start half failed, `cmd_restart` printed `✗ Restart command failed.` and returned 1 — with a healthy proxy already unloaded and the port dead. That wording reads like the restart was *declined*. It wasn't: the service was stopped, by this command, and stayed stopped. This happened in production during the v3.28.0 rollout — `launchctl bootout` succeeded, `launchctl bootstrap` returned `5: Input/output error`, and the proxy was down until someone noticed.
  - **The failure was transient, and one retry was enough.** The identical `bootstrap` succeeded by hand seconds later — unchanged plist, unchanged domain — and `ocp update` ran the same two commands successfully minutes afterwards. The plausible cause is a race against the `bootout` that just completed, which is what a short backoff fixes. Each resolved command now gets up to 3 attempts with a rising delay.
  - **The verdict now comes from the health probe, not from a subcommand's exit status.** A failing command does not prove the proxy is down — the service manager may have started it anyway — and a succeeding one does not prove it is up. So the failure branch no longer returns early; it falls through and measures.
  - **Four outcomes, four messages, where there were two.** The missing cell was the incident itself: a command failed *and* the proxy is not answering. That now says `✗ THE PROXY IS DOWN`, states that this command stopped it and could not start it again, and prints the exact start command the resolver produced for this host. The inverse cell — command failed but the proxy is answering — reports the service as UP with a warning rather than a silent `✓`, because silently swallowing it would train operators to ignore the retry warnings that are the early signal for the DOWN case.
  - **The local-`curl`-fault cell is reachable in two states and no longer describes them alike.** With a failed command it said "Restart command ran" — false, and contradicting the warning printed immediately above it — and offered no way back. It now says the command failed, that the proxy *may* be down because the stop half already ran, and prints the start command. The all-succeeded wording is byte-for-byte unchanged, pinned by a control test.
  - **What the DOWN message does not claim.** It reports what the probe measured just now, not that the service "will stay stopped": a service binding slowly after a *partially* failed plan may still be coming up. Polling `/health` to a deadline (as the update path's post-flight does) is **not** implemented here and is left as follow-up; re-running the printed start command is harmless if it turns out to be up.
  - **Exit-code contract, now in `ocp restart --help`:** 0 means the proxy answers `/health` afterwards, **not** that every command succeeded. A script keying on exit 0 as "the commands ran cleanly" needs to read the output.
  - **A local `curl` fault still yields `UNKNOWN`, never `DOWN`.** The new branch keys on "probe non-zero", and #299's local-fault arm is also non-zero; ordering keeps a machine that merely cannot *run* curl from being told its proxy is dead. A dedicated test pins the precedence, and a mutation confirms it can fail.
- **OCP's own inbound credentials no longer reach a spawned `claude`, on every spawn path (#328).** `spawnClaudeProcess` built the child environment as `{...process.env}` and stripped only four `ANTHROPIC_*` variables, so `PROXY_API_KEY` — the credential that authenticates callers **to** OCP — was handed to every child. The child is the one component that reads attacker-controlled text, and it has no use for that key: it authenticates to Anthropic with `CLAUDE_CODE_OAUTH_TOKEN` and never talks to OCP. `OCP_ADMIN_KEY` and `PROXY_ANONYMOUS_KEY` leaked the same way.
  - **Demonstrated, not theorised.** On a host running two OCP instances split by Unix identity — an unprivileged one backing an agent that answers untrusted users, a sudo-capable one for the operator — both configured with the *same* `PROXY_API_KEY`, an independent reviewer sent one benign-framed prompt: the child read the key from its own environment, called the privileged instance with it, and the resulting child confirmed passwordless sudo. The identity boundary was bypassed without ever being attacked. Sharing one key across instances is an operator error and was fixed there; the key reaching the child is OCP's.
  - **There were FOUR sites, not two, and two of them were found only by independent review.** The third was the one that mattered most. An independent review found `lib/tui/session.mjs` carrying its own copy of the same four-name denylist, so every secret reached the tmux pane. That is the **only** request path when `CLAUDE_TUI_MODE=true`: `server.mjs` selects `callClaudeTui` over `callClaude` wholesale, so a fix confined to `spawnClaudeProcess` would have left every TUI request unprotected while the changelog claimed otherwise. Both the pane's `env -u` prefix and the tmux **server's** own environment are scrubbed now — and the second is not merely belt-and-braces: with only the pane prefix in place, `tmux show-environment -g` **still returned all three secrets from inside the pane**, a cross-platform retrieval path, not just the Linux `/proc` one. **Scoped honestly:** that only holds when OCP starts the tmux server. If one is already running — which OCP's reap deliberately does not kill when foreign sessions exist, and OCP uses the default socket — the operator's own shell environment remains readable from the pane, and `ocp-connect` writes an OCP credential into that shell. A dedicated socket would close it; tracked as follow-up — a server started by OCP inherits OCP's environment and its panes inherit from the server, and OCP's boot reap calls `tmux kill-server`, which guarantees the next `new-session` rebuilds it under that environment. So the leak was the default path, not an edge case.
  - **The fourth site is `setup.mjs`**, which carried its own copy of the same denylist on its `claude -p` auth probe (and no `env` option at all on `claude --version`, so that one inherited everything). Lower severity — that child's prompt is the literal `"ping"`, so the injection chain of this issue is not reachable through it — but it is reached by `ocp update`, and leaving it would have kept the "remember to extend it everywhere" defect alive. **Stated plainly: the `setup.mjs` fix has no test.** Reverting it leaves the suite green. Running the real `setup.mjs` in a harness writes configs and installs autostart, and this repo has an incident from a test harness doing exactly that, so building one for a P1 with no injection path was judged the wrong trade. It is a declared gap, not an oversight.
  - **A per-user key from `ocp keys add` is invisible to both of the earlier passes, and that is the multi-user case.** `scrubInboundAuthEnv` can only remove a value it can *see* — the three named credentials in the parent environment. But `ocp-connect`'s documented flow when the remote requires auth issues a key from OCP's SQLite store, which is neither of those names nor equal to any of their values. In multi mode `PROXY_API_KEY` is typically unset, so the by-value pass is **entirely inert**: measured, `removed: []` with the per-user key reaching the child untouched. A third pass matches by **format** — every OCP-issued key is `ocp_` plus exactly 32 base64url characters by construction (`keys.mjs`) — so it is caught under any variable name, while a real OpenAI key (`sk-…`) cannot collide. The pattern is asserted against a genuinely minted key rather than a literal, so changing the key format fails a test instead of silently disabling the pass.
  - **The TUI pane prefix now covers aliases too.** It is a list of names, so it could not express "whatever variable carries the credential" — which mattered precisely in the foreign-tmux-server case where the server-env scrub never applies and the prefix is the only defence.
  - **Deleting by NAME was not enough, and OCP itself is what proved it.** `ocp-connect` writes the user's OCP credential into **`OPENAI_API_KEY`** — every shell rc, `launchctl setenv`'s user domain on macOS, `~/.config/environment.d/` on Linux — and `docs/lan-mode.md` teaches the same by hand. OCP's own autostart runs in exactly those two scopes. So on any host that has run `ocp connect`, the same secret still reached the child under a name the list does not contain, and **#328 was not closed**. A reviewer demonstrated it end to end against a real server. `scrubInboundAuthEnv` now also removes any variable whose **value** is one of the inbound credentials, whatever it is called. Not by adding `OPENAI_API_KEY` to the name list: a child can legitimately need a real OpenAI key via an MCP server, and the goal is to remove OCP's credential, not that variable. Values shorter than 8 characters are matched by name only, so a one-character key cannot strip every flag that happens to share its value — a stated limit, not an oversight.
    - **The test already described this threat while the code could not implement it.** `the VALUE of <name> reached the child under some other name` has been in the assertions since the first revision; it could never fire, because the implementation deleted by name. Both now agree, and a mutation proves the assertion is live.
  - **The declared gap is closed, and the reasoning that declared it was wrong.** An earlier revision called `setup.mjs`'s two sites untestable because running the real `setup.mjs` writes configs and installs autostart. A reviewer pointed out the false dichotomy: the choice was never "run it or don't test it", it is "run it or **slice** it" — the technique `AGENTS.md` endorses for `ocp-connect`. Both sites are now covered by slice tests that spawn nothing and write nothing, and each fails independently when its own site is reverted.
  - **A frozen list, not four more `delete` lines.** `INBOUND_AUTH_ENV_VARS` + `scrubInboundAuthEnv()` in `lib/spawn-auth.mjs` are what every site calls. The ten: `server.mjs`'s two binary lookups, its auth probe, its `-p` spawn and its keychain read; `lib/tui/`'s pane prefix and tmux server env; `setup.mjs`'s three spawns. Those two sites had already drifted in purpose, and a denylist you must remember to extend in both places is precisely the failure mode that produced this. A new inbound-auth variable is added in one place.
  - Deliberately **not** stripped: `CLAUDE_CODE_OAUTH_TOKEN` (an outbound credential the child genuinely needs — an integration assertion pins that it reaches the child. The isolated-spawn branch also re-injects it downstream of the scrub — but only under `decision.isolated && decision.token`, so on a real-HOME fallback (`OCP_SPAWN_REAL_HOME=1`) a scrub-site edit **would** break requests. The earlier unconditional wording was wrong) and `PROXY_ADVERTISE_ANON_KEY` (a boolean flag, not a secret).
  - **Scope, stated rather than implied:** this stops OCP from *handing* the credential to the child. It does not put it out of reach — the child runs as the same Unix user, so on Linux it can still read the parent's `/proc/<pid>/environ` or the 0600 unit file if it has `Bash`. Defence in depth is the claim; "the child cannot obtain it" is not.
  - Presence, not truthiness: an empty-string secret is still removed. `if (env[name])` would leave the *name* visible to the child, and a mutation proves the distinction is tested.
  - **Sixteen tests, all behavioural.** The fake `claude` dumps its own environment and the assertions read it; nothing greps source. **Seven of the ten scrub sites are covered separately** (six before review 5, which found the alias layer unpinned) — reverting any one of those turns exactly one test red while the others stay green, so a partial fix cannot pass there. The remaining three (`server.mjs`'s two binary lookups and the macOS keychain read) are scrubbed for consistency and are **not** test-pinned: none reads attacker-controlled text, and `server.mjs` cannot be imported by the suite. Stated rather than glossed — an earlier revision of this entry claimed all of them were covered, and a reviewer disproved it by mutation. Each test also asserts a control (the capture is non-empty and looks like an environment) so a broken capture cannot satisfy "no secret found" vacuously.
- **The auth probe could wedge at a stale `auth.ok=false` and block `ocp update` forever (#324).** Two individually-correct rules composed into a trap: a conclusive non-zero exit latches `ok:false`, and an inconclusive probe (timeout / spawn failure) deliberately *preserves* the last conclusive verdict — right on its own, since a timeout measures host load rather than credential validity. Together they mean **only a conclusive success can clear the latch, and a probe that reliably times out never produces one.** Observed in production: a host served 51 requests with zero errors and `/health` reported `ok` throughout, while `ocp update` refused for hours with `Pre-upgrade check failed: fix_oauth`. The only symptom was the upgrade path being shut, and nothing anywhere said "stuck".
  - **Additive under ADR 0012.** New field on `/health`: **`auth.consecutiveInconclusive`** — consecutive inconclusive probes since the last conclusive one, reset to 0 by *both* conclusive outcomes. It is the first change to use ADR 0012's standing authorization.
  - **`auth.ok` is deliberately unchanged.** The last conclusive verdict really was `false`; rewriting the rule that determines a grandfathered B.2 field's value would be a contract change needing its own ADR (the ADR 0010 test). Staleness lives in the new counter, and only a consumer that must *decide* something reads it.
  - **`/health`'s `status` cannot move because of this.** `proxyHealthStatus` reads `consecutiveFailures`, never `ok`, and inconclusive probes still do not touch that tally. A test asserts both.
  - **`doctor` is where the decision changed.** `classifyAuthOk` now returns WARN instead of FAIL when a latched `false` has at least `AUTH_STALE_AFTER_INCONCLUSIVE` inconclusive probes behind it **and the most recent probe did not conclude**, so `next_action.kind` is no longer `fix_oauth` and the upgrade proceeds. A genuine, current rejection still FAILs — pinned by a control test, because deleting the FAIL branch would be a far worse bug than the one being fixed.
  - **Backward compatibility is pinned too.** During an upgrade, `/health` is read from the *running* (older) server, which does not emit the new field. An absent or non-numeric counter reads as 0 — never as "stale" — so a pre-#324 server keeps reporting real rejections to the gate.
  - **The counter alone was not a sufficient condition, and only mutation revealed it.** An independent reviewer made the server *preserve* the counter on a conclusive rejection instead of resetting it — the whole suite stayed green, while the resulting state (`ok:false`, `lastOutcome:"rejected"`, counter ≥ 3) would have been read as stale and unlocked the gate **seconds after a conclusive rejection**. The decider now also requires the most recent outcome to be inconclusive. A correct server can never emit that combination, so this is strictly tightening on correct servers and a backstop against an incorrect one — and the producer's reset is now pinned from its own side too, in the order (inconclusive first, then rejection) that the original test could not reach.
  - The threshold lives in `lib/constants.mjs` (`AUTH_STALE_AFTER_INCONCLUSIVE`), not in either consumer: a threshold the producer and the decider disagree about is exactly the drift that file exists to prevent.

Read together, most of this batch is one shape of bug, hit independently at a dozen call sites: **a check's own failure to run got treated as the answer it would have given if it had run and found nothing.** A hard-coded restart target got "restarted" whether or not it was the process actually holding the port. `cmd_restart` had no failure exit code at all. `lsof`/`curl`/`python3` simply being absent from `$PATH` looked identical, downstream, to each of them running cleanly and reporting an empty or negative result. The fix, repeated a dozen times across this batch, is always the same: distinguish "the command could not run" from "the command ran and told you something." First fixed at the request-diagnostics layer by #232 below, the same pattern turned out to also describe most of the control-plane tooling (`ocp update`, `ocp restart`, rollback, and the bash CLI's own status commands).

The other thing worth reading in its own right, because it changes exit codes on scripts people may already have automated around: **`ocp update --target` now behaves consistently everywhere it appears, and that consistency is enforced by refusing rather than by silently doing the old thing.** See Changed below before you script around it.

`server.mjs` is untouched by every PR in this entry except #232 (unchanged from the existing write-up below) — confirmed by diffing every one of the other 36 merge commits against `server.mjs` individually.

### Changed

- **`ocp update --target <version>` is now honored or refused everywhere it appears — previously it was silently honored on only one of five paths and silently dropped on the other four.** `doctor`'s `next_action.kind` has five real update-shaped values (`noop`, `restart`, `update`, `upgrade`, `fresh_install` — `fix_oauth`/`fix_service` already exit non-zero on their own paths and were never affected). Before this batch, the *same* `ocp update --target vX.Y.Z` command silently pinned or silently didn't, depending only on where the host happened to sit in the release cycle:
  - **`upgrade` (cross-minor, the full path)** — was silently ignored (checked out `doctor.latest_version` regardless of the pin); now **honored for the `--target vX.Y.Z` (space-separated) form** — validated (`^v?\d+\.\d+\.\d+$`, and must be strictly newer than the current version — no accidental downgrades through this path) and threaded into the `git checkout` step (#257/#259). An independent review of that fix additionally found the interpolated value shell-injectable and firing *before* the tag-existence refusal; both fixed in the same PR before anything shipped past review.
  - **`update` (light/patch-bump, the single most common invocation)** — silently ignored; now **prints an explicit warning and remains a no-op** (#241/#255). This path is a `git pull --ff-only`, not a tag checkout, so honoring the pin for real would mean swapping the underlying mechanism — deliberately scoped out as a separate, larger decision, not bundled into a warning fix.
  - **`noop` and `restart`** — silently accepted the flag and dropped it with **no signal at all**; now **refused outright by bash itself, non-zero exit, before any state changes** (#260/#272), via a shared `_detect_target_flag` helper that recognizes both `--target v1.2.3` and `--target=v1.2.3` and is also reused by the light-path warning and `--check`'s own preview. **`fresh_install`** gets the same refusal, but from `scripts/upgrade.mjs` rather than bash — reachable only through the space-separated form (see the caveat below).

  **Caveat, found by an external review of this reconstruction and verified against the code:** the refusal/honoring logic in `scripts/upgrade.mjs` (the `upgrade` and `fresh_install` rows above) still parses argv with a plain `args.indexOf("--target")` — it does not recognize `--target=vX.Y.Z`. `ocp update --target=vX.Y.Z` on either of those two paths silently behaves as if no target were given at all: `upgrade` falls back to `doctor.latest_version` exactly as before this batch, and `fresh_install` does not refuse. `noop`/`restart` are unaffected — their refusal runs entirely in bash, ahead of `scripts/upgrade.mjs`, via `_detect_target_flag`, which does handle both forms. This equals-form gap on the Node-side paths is being tracked as its own issue, not fixed by this batch.

  **Upgrade note:** if you have automation invoking `ocp update --target <version>` unconditionally, audit it against the behavior above before upgrading past this point — specifically anywhere that assumed a bare `ocp update --target` was always either a real pin or a harmless no-op, and anywhere that uses the `--target=vX.Y.Z` form on a path doctor might resolve to `upgrade` or `fresh_install`.

- **`ocp update`'s `fresh_install` path (pre-v3.4.0 hosts) now requires an explicit `--fresh-install` flag in addition to `--yes` (issue #227).** #217/#260 reconnected this arm, but its real `ai_executable` steps (`mv ~/.ocp ~/.ocp.backup-<epoch>`, `rm -rf ~/ocp`, a fresh `git clone`, `node setup.mjs`) have never been execution-verified — not in CI, where the test suite only ever reaches `runFreshInstall()` with `execSync` mocked out, and not by hand. `--yes` alone — the same flag every other non-interactive `ocp update` invocation already passes, including doctor's own suggested remediation for `update`/`upgrade`/`restart` (`ai_executable: ["${ocpDir}/ocp update --yes"]`) — no longer runs it: a bare `ocp update --yes` on a host doctor classifies as `fresh_install` now refuses, naming the doctor conclusion, the explicit command to opt in (`ocp update --fresh-install --yes`), and where to read the limitation. `ocp doctor --json`'s `next_action` is unchanged — only automatic execution through `ocp update` is gated; the ai_executable steps it lists were already fully explicit. See `docs/upgrading.md`'s "Old version (< v3.4.0)" section and the README Troubleshooting bootstrap-quirk entry for the full statement of what has and hasn't been verified.

### Fixed

- **A successful `ocp update`, `ocp restart` or rollback no longer reports failure — and `ocp doctor` no longer prints `auth.ok=false` for a value that is `null` — on a host whose auth probe timed out (#289).** ADR 0010 (shipped as #275, immediately above) correctly made a probe timeout **inconclusive**: `auth.ok` holds the last *conclusive* verdict, so a timeout preserves it rather than recording a rejection, and `/health` keeps reporting `status: "ok"`. What did not change was the consumers. Every one of them still required a strict `auth.ok === true`, with retry budgets two orders of magnitude smaller than the window in which `null` persists — `postFlightOk`'s budget is 10 × 1s, the next probe is up to 600s away, and an inconclusive result does not shorten that wait. Post-flight only ever runs against a *freshly restarted* process, which by definition has no earlier conclusive verdict to preserve, so on exactly the loaded host ADR 0010 was written about, `auth.ok` was `null`, `null !== true`, and a restart that had worked was reported as a failure — with `runRollback` throwing `rollback post-flight failed: restored tree may not be what's running` about a rollback that had succeeded.
  - **`postFlightOk` now asks the question it actually needs answered**: `status === "ok"` plus the version match, instead of `auth.ok === true` plus the version match. `status` is the field ADR 0010 built specifically to answer "can this proxy serve", which is what post-flight is verifying about the process now holding the port. The version arm is untouched, so #173's orphan-holds-the-port case still fails exactly as before. The trade is deliberate in both directions: the new predicate is **stronger** against an unusable `claude` binary (which makes the probe fail to *spawn* — inconclusive — so a stale `auth.ok: true` used to survive it, while `status` goes `degraded`), and **weaker** against a single conclusive rejection (ADR 0010 holds that one rejection is a token-rotation race, not a condition; a real credential outage is caught before this point, by `ocp doctor` selecting `fix_oauth` and `ocp update` refusing to run).
  - **`ocp doctor` stops asserting a state that did not occur.** Both call sites (the full run and the `--check oauth` fast path) used a falsy check, which put `null` on the same branch as `false` and then described it with a hard-coded `auth.ok=false` string. They now share one `classifyAuthOk()` helper that keeps the three-valued domain three-valued: `true` → PASS, `false` → FAIL (unchanged — still selects `fix_oauth`), `null`/absent → **WARN**, reporting the value actually observed (`auth.ok=null`, plus `lastOutcome`) instead of a literal. WARN rather than FAIL because a FAIL here is a decision, not a label: it selects `next_action.kind = "fix_oauth"`, whose remediation is "reinstall the claude binary", and it makes the next `ocp update` refuse — neither of which is a correct response to "no probe has concluded yet", which on a freshly restarted proxy is the *expected* state for up to one probe interval.
  - **The suite now replays ADR 0010's own motivating incident through every consumer and asserts each consumer's decision**, not just the endpoint payload — `postFlightOk`, `runPostFlightCheck`, `runRollback`, both `doctor` paths, `ocp-plugin`'s `/ocp health` and `/ocp status` (driven through the real plugin over real HTTP), and `dashboard.html`'s Status card. That gap — reasoning about consumers in prose while testing only the payload — is what let this ship. ADR 0010's consumer enumeration itself carried three factual errors, now corrected in place in the ADR rather than deleted.
  - **`ocp doctor --check oauth` now counts its warnings.** `runOauthOnly` hard-coded `warn_count: 0`, which was true while that path could only emit PASS or FAIL and became false the moment a WARN became reachable there — printing `Summary: 0 FAIL, 0 WARN` directly beneath the `[WARN] oauth_ok` line it had just emitted, and under-reporting to any agent reading `--json`. Found by independent review of this change: the same hard-coded-literal-asserting-an-unobserved-state defect, reintroduced inside the fix for it. `warn_count` is now derived from `checks` on both doctor paths, and is asserted non-zero by tests so it cannot silently return to a constant.
  - **Fleet note:** v3.26.0 does not have this defect, because it does not have ADR 0010 either. Anything already updated to a `main` newer than #275 does.

- **Restart, rollback, and `cmd_restart` no longer guess which process owns the OCP port — they resolve it from live state and refuse when they can't tell (#214/#217, #215/#221/#249, #226/#229, #220/#230, #233/#240, #237/#251, #239/#265, #254/#268, #234/#250, #253/#271, #277, #280, #238/#244, #263/#270).** Before this batch, every restart path in OCP — the cross-minor upgrade phase, the `--rollback` phase, and bash's own `cmd_restart()` (used by `ocp restart`, the patch-bump update path, and direct restart) — pointed at a single hard-coded unit name (`ocp-proxy.service` / `dev.ocp.proxy`) with no check that it was actually the process holding the port. A live incident showed this "restarting" a user-scope unit while a system-scope unit was the real listener, leaving an orphan `server.mjs` unable to bind, while every layer reported success — `cmd_restart` in particular **had no failure exit code at all**; every path, success or not, fell through to an implicit `return 0`.
  - **The resolver (#221)**, plus **#217**'s earlier fix that catches the narrower "tree already updated, service never restarted" case (a new `next_action.kind: "restart"` path) and **#229**'s fix to stop `setup.mjs`'s reconfigure phase from re-enabling/starting a unit ahead of the restart phase (so it can't re-arm the same race), rebuilt the core logic in a new `scripts/lib/restart-unit.mjs`: on Linux, a leaf-to-root `/proc/<pid>/cgroup` walk identifies the real owning systemd unit (system vs. user scope); on macOS, `lsof`, cross-checked against `netstat` for `lsof`'s ambiguous exit-1/empty-stdout signature (a fix in its own right — **#240** — since that ambiguity had made the rollback-on-a-down-service recovery path unreachable on macOS). Any state the resolver can't confidently classify — an unattributable owner, a process not managed by any unit, a system unit needing sudo it doesn't have — **refuses with an actionable message rather than guessing**. **#230** adds a complementary static pre-flight check (`multi_unit_boot_race`) that warns on `ocp doctor`/`ocp update` when two enabled units (systemd or launchd) are both configured for the OCP port, independent of which one is live right now.
  - **#249** brought bash's own `cmd_restart()` onto this same resolver instead of its separate hard-coded fallback cascade (which included an `ai.openclaw.proxy`/`openclaw-proxy` legacy-name chain and an unmanaged `pkill`+`nohup` last resort) — and gave it a real exit code for the first time: a refusal now returns 1 instead of silently returning 0. **#270** applies the identical "distinguish couldn't-run from ran-and-failed" treatment to `cmd_restart`'s OpenClaw-gateway sub-step (OpenClaw is an optional sibling tool — its absence is now reported calmly and exits 0; a real failure to restart an installed gateway is now loud and exits 1; previously both crashed the whole `ocp` process identically via `set -e`).
  - Beyond the core resolver, four independently-discovered identity gaps were closed one at a time, each its own PR per Iron Rule 11: **#251** refuses when the resolved unit's live process is confirmed *not* to be `server.mjs` (closing a path where a misconfigured port pointed at an unrelated service like `nginx.service` and would have been restarted as if it were OCP's own); **#265** brings the same process-identity check to macOS via `launchctl print` (launchd has no `pid → label` lookup, so this asks the reverse direction — what PID launchd itself believes owns `dev.ocp.proxy` — and compares); **#268** adds a Linux-only, warn-only working-directory check so a second OCP checkout (e.g. a dev tree beside a production install) sharing the same process name doesn't get treated as the production instance — its first draft compared against a hard-coded default that was dead code in every real invocation, corrected to derive from the running module's own file location; and on the rollback side specifically, **#250** closes a guard gap where a mismatched *user-scope* unit (as opposed to system-scope, already refused) fell through untouched, and **#271** fixes the rollback fallback's warning to name a real second enabled unit instead of asserting none exists.
  - **Rollback also gains a real post-flight check for the first time (#277)**: it previously reported success unconditionally once the restart command exited 0, never confirming the restored tree actually came back up serving the right version. It now verifies `/health.version` against the snapshot's own recorded `fromVersion` (deliberately not `toVersion` or `doctor.latest_version`, either of which would check against the wrong target). **#280** hardens the rollback git-checkout itself: the snapshot's recorded commit SHA is now shape-validated (`^[0-9a-f]{7,40}$`) and passed via `execFileSync`'s argv form instead of a shell-interpolated string — defense-in-depth, not a live vulnerability today (the value is generated by OCP's own `git rev-parse HEAD`, not attacker-reachable), mirroring the same hardening #259 already applied to the sibling upgrade-path checkout.
  - **Platform scope is explicit, not incidental.** Linux restart-target resolution is complete: unit identity, process identity, foreign-unit refusal, working-tree match, and rollback-specific guards are all live and covered by CI. macOS is narrower by design — #240 and #265 brought it listening-state and unit/process-identity parity, but the working-tree check (#268) has no macOS equivalent (no `/proc`), and per #265's own review record, the entire darwin branch runs nowhere in this repo's CI (Linux-only runners) — verified only live, read-only, against a real host.
  - **#244** is a documentation-only sweep, correcting eight places that still described #221 as unmerged after it had actually landed — the same category of staleness this very changelog entry exists to fix, at smaller scale.

- **A dozen places in the bash CLI (`ocp`) and installer (`setup.mjs`) that ran `curl`, `lsof`, `netstat`, or `python3` could no longer tell "the command itself didn't run" from "it ran and told us the real answer is negative or empty" (#256/#258, #242/#252, #261/#267, #246/#269, #246/#285, #273/#279, #278/#286).** The shape repeats: `2>&1`-into-capture, a bare pipeline under `set -euo pipefail`, or a catch-all that discards every failure identically — so a missing binary (shell exit 127, "command not found") produced the same "proxy unreachable" or empty-JSON output as the binary running cleanly and reporting nothing. Two shared helpers now anchor most of this surface: `_curl_or_die()` (introduced in #267; wired at 14 curl call sites across `ocp` — `usage`, `usage --by-key`, `keys add`, `keys revoke`, `keys` (list), `status`, `settings` GET/PATCH, `health`, `logs`, `models`, `sessions`, `clear`, and `connect`'s own initial reachability probe) and `_pyfail()` (introduced in #252, covering the nine-then-ten `curl | python3` display commands with a raw-JSON fallback plus a loud warning instead of silent death). `setup.mjs`'s two bare `lsof`/`netstat` sites (the `start.sh` port check that gates whether a second `server.mjs` gets `nohup`'d, and the post-install bind check — two distinct checks, not one) got the same treatment via a new extracted module, `scripts/lib/start-sh.mjs` (#269, #285), though the two checks diverge in how far the fix reaches on each platform: the `start.sh` port check moves to absolute-path `lsof`/`netstat` plus a `netstat` cross-check on macOS (a restricted `PATH`, e.g. a launchd job's default environment, can omit `/usr/sbin` entirely) but stays a bare, non-absolute-path `lsof` on Linux, deliberately; the post-install bind check moves to absolute-path `lsof` only (no cross-check) on macOS, and uses a bare `ss -tlnp` — not `lsof`/`netstat` at all — on Linux. Separately, **#258** fixed a real crash in the same neighborhood: `ocp usage --by-key` and `ocp keys` could hit bash 3.2's `set -u` unbound-variable error on macOS's stock shell when no admin key is configured (the default), which is exactly the shape this whole cluster is about — a real failure, mislabeled or swallowed.
  - **Not every curl call site in `ocp` went through this fix — verified directly, not assumed.** `cmd_lan`'s own reachability probe is still a bare `curl`; a missing `curl` binary makes it print "✗ Not LAN-accessible (bound to localhost only)" — actively wrong, not just silent, since the service may be correctly LAN-bound and the real problem is that `curl` itself never ran. `cmd_connect`'s onboarding flow has the same gap in its own later steps: the initial health probe is wrapped (`_curl_or_die`, counted above), but its subsequent `/v1/models` access check and `/v1/chat/completions` smoke test are both bare `curl`, unwrapped. So is `cmd_restart`'s own post-restart confirmation probe — on a missing `curl`, it prints "✗ Proxy not responding after restart" regardless of whether the restart actually worked, the exact failure mode this whole cluster exists to close. None of these three are fixed by any PR in this range; each is being tracked as its own issue.

- **`ocp update --dry-run` on the light/patch-bump path silently performed a real update, and a missing `python3` silently killed `ocp update` before it printed anything (#235 and #236, found and fixed together in #243, the same PR that also built the bash CLI wiring harness tracked as #225).** `_cmd_update_light` never forwarded its arguments and had no `--dry-run` handling at all, so the flag was accepted and ignored; fixed by mirroring the restart path's existing preview-then-return behavior. Separately, one WARN/INFO formatting block inside `cmd_update` piped into `python3 -c "..."` without the `|| true` fallback its sibling line already had, so under `set -e` a host lacking `python3` died silently mid-dispatch, before `cmd_update` ever reached its own kind-dispatch logic. Both were found while building a new bash CLI wiring harness for `test-features.mjs`, which several of the fixes above extend rather than duplicate.

- **The auth health probe no longer blocks the event loop, and one bad probe no longer reports `degraded` for ten minutes (#232).** Two defects in the same eight lines. **(A)** `execFileSync(CLAUDE, ["auth","status"], { timeout: 10000 })` sat inside an `async function`, which does not make a synchronous call asynchronous — it froze the whole process for up to 10s at boot (*before* `server.listen()`, so the proxy could not even begin serving) and again on every 10-minute tick. It is now a real async `execFile`, with a module-level in-flight guard so a tick landing on a still-running probe is skipped instead of stacking another spawn onto an already-slow host. The 10s timeout is deliberately unchanged: it bounds a stuck child, and lengthening it would only widen the window in which the verdict is stale. **(B)** `status` was `binaryOk && authStatus.ok !== false ? "ok" : "degraded"` — duplicated verbatim in `/status` and `/health` — so a single failed probe pinned `degraded` until the next tick. Captured in production: `/health` said `status=degraded, auth.ok=false, "spawnSync ... ETIMEDOUT"` in the same minute `POST /v1/chat/completions` returned 200. Probe outcomes are now classified (`authenticated` / `rejected` / `timeout` / `unavailable`), and only a **conclusive rejection** (a numeric non-zero exit) counts: a timeout or spawn failure preserves the last known `auth.ok` and leaves the tally alone, because a probe timeout measures host load, not credential validity. `degraded` now means the `claude` binary is unusable **or** the probe has returned **2 consecutive** conclusive rejections, evaluated by one shared `proxyHealthStatus()` helper used at both sites so the two expressions cannot drift apart again. Value domain is unchanged (`ok` / `degraded`). Semantics change to two grandfathered Class B.2 endpoints, authorized by **[ADR 0010](docs/adr/0010-health-verdict-semantics.md)** per ADR 0006 ¶39/¶109; no `cli.js` citation applies (`/health` and `/status` are OCP-owned surface).
  - **Downstream behaviour change, called out deliberately:** `auth.ok` now survives an inconclusive probe. The consumer this actually changes is `scripts/doctor.mjs` (`:668` / `:869`), which reads `auth.ok` with a falsy check: against a long-running instance that has a prior conclusive success and a recent inconclusive probe, `oauth_ok` now PASSes where it previously FAILed. It does **not** change `ocp update`'s post-flight check — `runPostFlightCheck` only ever runs against a freshly restarted process, where `auth.ok` is `null` and there is no earlier verdict to preserve, so `postFlightOk` returns `false` exactly as before. (`ocp update` does benefit from the async probe itself: `/health` is reachable within milliseconds of boot instead of after a blocking probe, so the retry budget is no longer spent on connection-refused.)
  - **Correction, added with #289 (see the entry above):** that last sentence is true of the *return value* and misleading about the *outcome*. The value `postFlightOk` returns "exactly as before" is `false` — on a restart that succeeded. Reporting a working update as a failure is a behaviour change in everything except the function's return type, and it was shipped as a non-change because only the return value was checked. #289 is the fix.

## v3.26.0 — 2026-07-27

Maintenance release. One user-visible change — advertised `maxTokens` now tells the truth — and four rounds of repairs to the machinery that is supposed to catch mistakes: a schema for the model SPOT, a release-job bug that would have shipped an empty release body, and the integration-test harness that had been failing 4 runs in 5 without anyone noticing.

Every PR carried an independent fresh-context reviewer (Iron Rule 10). Two reviewers refuted the author's stated rationale while the change itself stood; in both cases the rationale was rewritten rather than the finding waved off, and one reviewer retracted its own earlier finding after the evidence was re-derived. `server.mjs` is untouched in this release, so no `cli.js` citation applies.

### Changed

- **`maxTokens` now matches the CLI registry (#195).** The previous values were not uniform: six entries were 16384 and `claude-haiku-4-5-20251001` was 8192. Every Opus entry and `claude-sonnet-5` go to **64000**, `claude-sonnet-4-6` and `claude-haiku-4-5-20251001` to **32000** — the `max_output_tokens.default` each model declares in the compiled CLI 2.1.220 registry. Every model except `claude-sonnet-4-6` (1.95x) moves by the same 3.91x — haiku included, from its lower base. The value is consumed only by clients that choose to honour it, via `setup.mjs` / `scripts/sync-openclaw.mjs` / `ocp-connect`. **Expect no change in answer length or quota burn.** `ocp-connect`'s independent family table moves to the floor over each family's current `models.json` members (opus 64000, sonnet 32000, haiku 32000), since prefixes cannot distinguish versions. Its unknown-id fallback stays at **8192** — the registry's global minimum, held by `claude-3-5-haiku` and `claude-3-5-sonnet`, which are the only real ids that reach it (`claude-3-5-*` matches no family prefix).

### Added

- **`models.schema.json` — the model SPOT now has a schema, enforced in CI (#196).** `models.json` declares it via `$schema`, and `test-features.mjs` validates the SPOT against it using the repo's **own** `validateJsonSchema` from `lib/structured-output.mjs` — no new dependency. A malformed entry now fails the build instead of surfacing downstream in OpenClaw. The schema's description names exactly which keywords that validator enforces and which it **silently ignores** (`minimum`, `maxLength`, `pattern`, `uniqueItems`, …), so nobody adds a constraint that buys nothing; those go in `test-features.mjs` instead. Guard tests cover 8 distinct corruptions plus uniqueness and whitespace on every name field.

### Fixed

- **`release.yml` would have produced an empty release body on any repo state without `CHANGELOG.md` (#202).** The no-changelog branch set an output pointing at a notes file it never wrote, and the create step then read a missing path. Rare, but it fails exactly when you least want it to — during a release. The branch now writes the file.

### Fixed

- **Cache keys hashed the alias, not the model it resolves to (#194).** `model` enters `cacheHash` exactly as the client sent it, so a request for `"opus"` was cached under the literal `"opus"` — and since `models.json` is read once at boot while the SQLite `response_cache` outlives a restart, repointing an alias kept serving the **old model's** answers under it until TTL expiry. That would have silently defeated this release's own `opus` repoint for anyone running with the cache on. All three call sites now hash `Object.hasOwn(MODEL_MAP, model) ? MODEL_MAP[model] : model`, which fixes the normal, structured **and** single-flight keys at once and covers `legacyAliases` for free, with precise invalidation (only the repointed alias's entries change key) rather than a whole-cache flush. The increment now sits immediately after `activeProcesses.add(proc)`, structurally pairing it with the decrement; no reconciliation pass and no try/catch. Observability-only field, so no admission decision changes.
- **TUI: the host `CLAUDE.md` could leak into proxied turns (#187, contributed by @sumlin).** The TUI pane now spawns with `--safe-mode`.
- **TUI: `shift+tab to cycle` is accepted as an input-ready marker (#188, contributed by @sumlin).** Claude renders one of two ready-state footers depending on the build — the classic `? for shortcuts` hint, or `shift+tab to cycle` (as part of `⏵⏵ bypass permissions on (shift+tab to cycle)`) on newer 2.1.x. The matcher only knew the classic string, so on those builds it silently reported "never ready": every boot timed out with `tui_pane_not_ready`, and with the warm pool on, every pre-boot failed.
- **`OCP_LOCAL_TOOLS` no longer hard-codes a tool list in its wrapper (#191, closes #185).** The positive wrapper claimed a fixed set of tools regardless of `CLAUDE_ALLOWED_TOOLS`, so a narrowed tool surface was described inaccurately to the model.

## v3.14.0 — 2026-05-10

### Features (security hardening)

- **Per-key session isolation** (PR #86, S1) — the `sessions` Map in `server.mjs` is now keyed by `${keyName}|${conversationId}` instead of bare `conversationId`. Before this fix, two clients using distinct API keys but the same `session_id` value (e.g. both defaulting to `"default"`) would share the same `cli.js` subprocess and conversation history, creating a cross-tenant leak path. Post-fix each (key, session) pair is isolated end-to-end, extending the per-key cache isolation shipped in v3.13.0 D1 to the session layer.
- **On-disk credential file modes 0700/0600** (PR #87, S2) — `setup.mjs` now creates `~/.ocp` at mode 0700 and both `admin-key` and `ocp.db` at mode 0600. An idempotent `reconcileFileModes()` call in `server.mjs` startup tightens any existing installation to these modes automatically on every launch, so existing prod boxes fix themselves without manual `chmod`. Before this fix, all three files were created at the process's default umask (typically world-readable 0644 / 0755), leaving plaintext credentials readable by other local users.
- **`/api/usage` default scope = self; admin all-keys requires `?all=true`** (PR #88, S3) — the usage endpoint now applies a least-privilege default: anonymous callers receive only their own rows, non-admin authenticated callers receive only their own rows, and admin callers receive only their own rows unless they explicitly pass `?all=true`. When `?all=true` is used, an audit log line is emitted. Before this fix, any admin-token holder could silently enumerate usage data for every key on the server.

### Behavior changes

- **Breaking change for admin tooling**: `/api/usage` no longer returns all-keys data by default. Existing cron jobs, dashboards, or scripts that rely on the admin token seeing all-keys output must add `?all=true` to their request URL after upgrading to v3.14.0.
- **File mode reconcile at server startup** logs a one-line notice per path when mode is tightened (e.g. `[security] tightened ~/.ocp/ocp.db → 0600`). No action is required from the operator; the reconcile is idempotent and silent when modes are already correct.
- **`sessions` Map key is now `${keyName}|${conversationId}` internally.** No client-visible wire change — the `session_id` field in request/response is unchanged.

### Verification

- Stress-test pass: 11/11 phases including S1/S2/S3 security regression checks (Phase E, I, J). 35-minute sustained run, 60 calls, 0 errors, 0 timeouts. RSS dropped 51→47 MB across the window. Per-key cache isolation, singleflight, cache_control bypass, quota enforcement, file-mode reconcile, and scope guard against escalation all verified against running code.

### Governance

- All three PRs (#86, #87, #88) include the explicit `cli.js`-citation-not-applicable disclaimer (per PR #75 pattern) since they are OCP-internal access-control, session-state, and file-permission changes with no corresponding `cli.js` operation to cite.

This release adds no new env vars or endpoints. The only externally visible change is the `/api/usage` scope guard (breaking for admin all-keys consumers; see Behavior changes above).

## v3.13.0 — 2026-05-07

### Features (cache layer hardening)

- **Per-key cache isolation** (D1) — the cache key now includes the API key id, so distinct keys never share cache entries. Anonymous/unauthenticated callers share one `anon` pool. Hash format upgraded to `v2`; legacy v1-format rows orphan and are reaped by the existing TTL cleanup interval (no migration script).
- **`cache_control` bypass** (D2) — when a request carries an Anthropic `cache_control` annotation (top-level or nested in a content array), OCP skips its own cache entirely. The caller is using Anthropic-side prompt caching deliberately, and OCP must not interfere. A `cache_skipped{reason: cache_control_present}` log line is emitted on bypass.
- **Chunked stream replay** (D3) — when a streaming request hits the cache, the cached content is now emitted as multiple SSE chunks (80 codepoints/chunk, codepoint-safe via `Array.from()`) instead of a single large delta. Multibyte characters (CJK / emoji) stay intact.
- **Singleflight stampede protection** (D4) — concurrent identical cache-miss requests now share one upstream `cli.js` spawn instead of spawning N processes. Followers receive byte-identical responses to what the leader returns. All-or-nothing failure semantics: if the leader errors, all followers receive the same error. Streaming-path singleflight is explicitly out of scope (TODO left for follow-up).

### Behavior changes

- `/cache/stats` response now includes additive fields `inflight` and `requesters` (current in-flight singleflight entries and total waiting callers). Existing fields `entries`, `totalHits`, `sizeBytes` are preserved unchanged.

### Governance

- New ADR [`docs/adr/0005-no-multi-provider.md`](docs/adr/0005-no-multi-provider.md): OCP stays single-provider (Anthropic via `cli.js` spawn). Multi-provider gateway refactor explicitly out of scope; cache improvements are explicitly in scope.
- Design spec for this release: [`docs/superpowers/specs/2026-05-07-cache-upgrade-design.md`](docs/superpowers/specs/2026-05-07-cache-upgrade-design.md).

### No new env vars / no public API surface change

This release adds no new env vars or endpoints. All four improvements are internal correctness/concurrency upgrades to the existing `CLAUDE_CACHE_TTL`-gated cache layer. No client-observable wire shape change.

## v3.11.1 — 2026-04-21

### Fixes
- Concurrency slot leak on subprocess timeout (#37). The request-timeout handler called `proc.kill("SIGTERM")` without decrementing `stats.activeRequests`. A subprocess stuck in a syscall that ignored SIGTERM would hold its slot until (or beyond) the 5s SIGKILL escalation actually reaped it. Slot release is now wired to `proc.once("exit", cleanup)` so every termination path — normal close, error, SIGTERM, SIGKILL — releases the slot exactly once.
